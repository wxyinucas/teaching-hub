# 学生仓库与证据契约

> 状态：当前高层边界。各周的接口、测试和提交动作，只有写进当周任务后才成为要求；不沿用[旧版契约](./student-repository-contract-v1.md)的里程碑周号。

## 后续持续系统的目录边界

以下结构用于 `ai-agents-project` 中的持续系统；何时建立、采用哪份起始基线及如何接续，由当周任务明确。

```text
course/                         教师任务、公开测试与固定数据
common/                         教师维护的公共能力
students/sXX/system/            学生唯一持续演化的系统
students/sXX/weeks/week-XX/     当周报告与允许公开的证据
```

持续系统启用时，每名学生由教师分配唯一公开代号 `sXX`，按实际名单扩展；代号不编码完整学号或姓名。约 30 人的规模不改变“一人一份系统、按周追加证据”的结构。学生只修改自己的目录；不为完成个人任务改写教师区、公共区或其他学生目录。

正式建立后，普通周持续更新个人 fork 的 `origin/main`，不使用 `dev-week-*` 分支；教师会给出公共代码的统一同步方式。

## W2→W3 的仓库接续

W2 是工作台热身，学生已将 `ai-agents` clone 到 `~/course/w02-workbench` 并完成本地 commit。W3 先沿用已打开的 W2 窗口接通 Agent，报告阶段更新同一仓库并进入 `week-03/`。W2 工作台代码不作为 W3 报告的实现基线；`week-03/` 使用自己的 `pyproject.toml`、`uv.lock` 和 `.venv/`，同时属于这份仓库已有的 Git 历史。

W3 材料唯一维护在 `ai-agents/week-03/`，教学网站只链接与说明，不另存下载副本；`ai-agents-project` 留作后续持续系统启用，两个仓库不是复制材料的流水线。完成报告后，学生保留当前 Git 历史，将教师 remote 保留为 `upstream`，个人 remote 设为 `origin`，上传包含 W2 与 W3 的同一仓库。本次不要求 fork、PR、公开代号或 `students/sXX/system/`；更新异常的备用求助提示见 W3 Guide 末尾。

## 证据随能力增加

- W1～W3：环境状态、命令输出、真实 API 响应，以及 W3 报告的公开测试、实际实验结果、PDF、diff 和 Git 记录；W3 不要求 CI。
- W4～W9：在唯一的 `system/` 中累计维护本地行情处理器，保留事前预测、运行轨迹、回归测试、故障定位与修复证据；不以手写比例评分。消息队列、网络服务和实时前端属于教师工程展示，不自动成为学生仓库要求，边界见[编程阶段专项设计](./w4-w9-progressive-programming-system.md)。
- W10～W15：数据来源及时间边界、模型与测试、受控订单计划、实际平台状态、账户前后变化、一次调整与两轮对照。未成交或 replay 必须按真实状态标注。
- W16：冻结版本、简短证据卡与个人书面核验；不安排逐人口头答辩或短视频。

公开仓库只保存合成数据、可公开的测试和脱敏摘要。凭证、完整账户响应、原始行情与未脱敏日志不进入学生工作区、Agent 对话、公开 Git 历史或 CI。真正下单的受信提交器必须与学生可写代码隔离，独立强制 paper 和风险限制；具体门槛见[Longbridge 决策](./longbridge-decision.md)。

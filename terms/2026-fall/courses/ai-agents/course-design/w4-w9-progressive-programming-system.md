# W4～W9：同一系统的渐进式编程入门

> 状态：W4～W9 的现行专项设计。它回答“六周共同维护什么、每周改变什么、教师工程展示与学生作业怎样相连”。周次总览仍以[16 周课程蓝图](./16-week-blueprint.md)为准，各周真正成为要求的接口、测试与动作以当周任务为准。

## 1. 冻结的设计结论

W4～W9 不是六个互不相关的语法练习。学生继续维护 W3 建立的同一份 `students/sXX/system/`，逐步把本地行情检查程序发展成一个小型的**历史行情逐步处理器**；课程内部可简称 replay。

它把已经保存的历史记录按时间顺序逐条交给处理逻辑，使学生能够观察值、状态、函数、模块、错误与测试怎样共同决定结果。W9 结束时，它仍然不是回测器、交易策略或券商客户端，不计算资金、订单和盈亏，也不连接真实账户。

课程同时维护一明一暗两种实现尺度：

- **学生必做核心**：足够小、确定、可测试，使用本地 CSV 与普通循环；学生必须能够运行、追踪、测试和验收。
- **教师工程展示**：可以使用多进程、网络通信、异步消息队列和实时前端，把同一事件合同与处理核心放进更真实的系统；学生不负责搭建基础设施，但要预测现象、辨认边界并解释证据。

设计原则是：

> 演示系统可以复杂，但每次要求学生观察的问题必须简单；学生实现可以简单，但接口应与复杂系统同构。

## 2. 学生最终维护的对象

学生系统保留 W3 的 `market-check`，并逐步形成一个新的本地入口，例如：

```bash
uv run --locked market-replay prices.csv --symbol AAPL
```

最低数据流为：

```text
本地历史 CSV
      ↓
Source：读取原始记录
      ↓
Replay Driver：按时间依次交付一行
      ↓
Processing Pipeline：校验、筛选、转换、更新状态
      ↓
Sink：打印或保存稳定摘要
```

第一版摘要只描述能够直接核验的价格路径，例如：

```text
symbol=AAPL
observations=3
first_close=100
last_close=101
up_steps=1
down_steps=1
flat_steps=0
REPLAY=PASS
```

它不评价这段价格变化是否构成好策略，也不产生买卖信号。其价值在于让一个短小、真实的数据流自然容纳变量、容器、分支、循环、状态、函数、文件、模块、异常、日志和测试。

### 2.1 四类职责

- **Source**：提供记录。W4～W9 的必做实现只读取本地 CSV；测试可以使用内存数据。
- **Replay Driver**：控制交付顺序，一次只把当前记录交给后续处理，不要求按照现实时间等待。
- **Processor**：校验、筛选、转换或更新内部状态；可以是普通函数，也可以在 W9 用极小对象表达可替换边界。
- **Sink**：把结果打印、保存或交给其他系统；保存不是处理正确性的替代证据。

学生代码不必从第一天就使用抽象类或复杂框架。前几周可以只是一个循环和几个函数，只有在已经出现替换需求后，W9 才引入最小适配器。

### 2.2 共同事件合同

本地循环和教师工程展示使用同一种最小事件语义。具体字段可在 W5 任务成稿时冻结，概念上类似：

```json
{
  "event_id": "AAPL-20260901-093000",
  "event_time": "2026-09-01T09:30:00",
  "symbol": "AAPL",
  "close": 100.0
}
```

本地代码可以直接使用 Python 对象；跨进程演示需要把同一信息序列化成 JSON 等稳定格式。所谓解耦不是没有耦合，而是把直接函数调用的耦合变成明确的数据合同。

## 3. 六周累计实现路线

| 周次 | 累计实现增量 | 本周主要概念 | 必须保住的旧行为 |
| --- | --- | --- | --- |
| W4 | 给现有 `market-check` 增加可选 `--trace` | 源码与运行、解释与编译、进程、`stdout`、`stderr` | 不开启追踪时，W3 的输出、错误与退出状态不变 |
| W5 | 增加 `market-replay`：选择一个标的，按时间处理记录，形成首尾价格及上涨／下跌／不变次数 | 值、变量、类型、容器、分支、循环、状态改变 | `market-check` 继续可用；第二份数据不能暴露硬编码 |
| W6 | 把读取、筛选、状态更新和结果渲染拆成少量签名明确的函数 | 参数、返回值、作用域、注释、调用链、报错堆栈 | 不增加外部功能；CLI 与输出合同不变，累计测试证明重构未改行为 |
| W7 | 把文件读取、数据标准化和处理逻辑拆成模块，并增加可选结果文件 | 文件 I/O、模块、数据变换、异常 | 非法时间、价格或空标的明确失败；旧命令及默认输出不变 |
| W8 | 针对教师提供的故障数据或故障实现，先增加回归测试，再定位和修复 | 测试、`print`、日志、调试器各自能证明什么 | 不以新功能为目标；修复后全部旧测试继续通过 |
| W9 | 把数据来源形成最小适配器，保留 CSV 实现，并用内存来源证明可替换；教师展示异步运行拓扑 | 模块边界、最小 OOP／适配器、进程与并发风险 | 本地同步版仍是必做基线；W10 增加新 Source 时不重写处理核心 |

W6 与 W8 故意不追求新的可见功能。它们分别让学生经历“行为不变的重构”和“已有系统的故障修复”，从而把维护本身变成可观察的开发工作。

## 4. 跨周维护合同

1. **只有一份系统。** 不建立 `week-05-project` 或复制六份源码；每周继续修改自己的 `students/sXX/system/`。
2. **外部合同累积生效。** 已发布的 CLI、默认输出、错误状态与安全边界，除非当周明确迁移，否则不得悄悄破坏。
3. **累计运行测试。** W9 不只运行 W9 测试，而是运行 W3 至 W9 的公开合同；新增测试不能代替旧回归测试。
4. **默认行为优先兼容。** 可选追踪、文件输出或新入口默认关闭，避免新能力改变旧调用者的结果。
5. **参考基线用于恢复，不用于每周重置。** 教师可在讨论结束后发布标准版；学生接续时保留原 commit，记录采用来源，再继续维护同一系统。
6. **未见数据不引入隐藏规则。** 最终可以使用一份数值未见过、但完全符合公开 schema 的 CSV 检查硬编码；验收规则本身必须公开。

## 5. 教师工程展示

教师展示不是另一个无关的炫技项目，而是给学生本地核心换一种运行拓扑：

```text
历史数据或后续真实数据
          ↓
       Producer
          ↓
   异步消息队列
          ↓
       Consumer
          ↓
  同一处理核心 handle(event, state)
          ↓
   WebSocket / SSE
          ↓
      实时前端
```

具体消息队列、后端与前端技术暂不冻结。选型首先服从本地可重复启动、可观察积压、故障后可恢复和现场有可靠 fallback，而不是追求技术清单。

完整系统不必等到 W9 突然出现。教师可以沿六周逐步开放同一套演示：W4 指认独立进程和输出通道，W5 让页面实时显示状态变化，W6 追踪一条消息经过的函数调用，W7 展示序列化与外部边界，W8 注入故障并比较日志和页面事实，W9 再公开完整异步拓扑及其与学生本地循环的对应关系。演示本身也持续维护，不为每周另造一个无关项目。

### 5.1 推荐的课堂画面

- 终端 A 运行 Producer，按固定节奏从历史文件发送记录；
- 终端 B 运行 Consumer，接收记录并调用与本地版同构的处理核心；
- 浏览器显示最新事件、处理进度、状态摘要、连接状态和必要的错误；
- 暂停 Consumer，Producer 继续发送，显示积压；
- 重启 Consumer，观察积压如何被继续处理；
- 选择性注入一条重复、乱序或非法消息，观察合同检查与错误证据。

第一版只需要一个队列边界。不要为了展示微服务而在每两个处理步骤之间都加入消息中间件。

### 5.2 每次演示只回答一个问题

复杂系统每次只开放一个观察问题，例如：

- Consumer 停止以后，数据去了哪里？
- 重启以后为什么可以继续，哪些状态没有恢复？
- 页面上的一个数字依次经过了哪些部件？
- 重复消息会不会被处理两次？
- 两个 Consumer 同时更新状态可能产生什么风险？

学生不需要实现队列或前端，但应先预测，再根据终端、队列状态、日志和页面事实修正判断。没有明确观察问题的动画只是一段展示，不算课程证据。

## 6. W9 阶段验收

W9 结束时，学生至少能够证明：

- W3 的 `market-check` 与 W4 的可选追踪仍然工作；
- `market-replay` 能处理一份未见过但符合公开格式的本地 CSV；
- 错误输入明确失败，不生成貌似合理的结果；
- CSV 数据来源可以被测试用内存来源替换，处理核心不用重写；
- W3～W9 累计公开测试全部通过；
- 能沿一条记录说明它从 Source 进入、经过哪些函数或模块、怎样改变状态并出现在结果中；
- 能指出一次重构或修复影响了哪些旧部件，以及哪项测试保护了旧行为；
- 面对教师异步展示，能把 Producer、Queue、Consumer、处理核心与前端对应到本地系统中的职责。

不以是否手写、是否实现异步系统、界面是否美观或价格摘要是否具有投资价值评分。

## 7. 与 W10 之后的衔接

W10 可以把 Longbridge 或教师 replay 包装成新的 Source／Producer，产生与本地 CSV 相同的事件合同；W4～W9 的校验、处理和证据结构继续复用。W11 才让可替换决策模型读取有时间边界的数据并输出目标持仓，W12 才通过教师受信设施接触模拟订单。

因此 W4～W9 不提前实现策略、账户、资金、订单、收益优化、真实网络凭证或券商提交器。教师的异步通信与实时界面展示工程可能性，但不改变学生代码和平台安全边界。

## 8. 教师试跑与退路

- 教师必须先在干净环境中跑通学生本地基线、累计测试和完整工程展示。
- 演示应保存不含账号、凭证和学生信息的真实终端输出或录屏；现场基础设施失败时切换到这些材料，不临时抢修服务。
- Producer、Consumer、队列状态和前端画面应能共同回答本次唯一观察问题；不为“更像真实系统”增加无法解释的部件。
- 故障注入必须可恢复，不使用真实账户、不可撤销操作或公开网络服务。
- Codex 可以生成和修改演示代码，但教师必须能说明关键数据路径、预期故障和恢复条件；Agent 自述不能代替课前试跑。

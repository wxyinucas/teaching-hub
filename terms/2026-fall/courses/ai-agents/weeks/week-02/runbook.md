- 根问题：一处很小的网页修改，怎样经过远端仓库、另一台机器和项目环境，最后仍然按照我们的预期出现？

**任务名称：不影响未来的本节课实验。** 不检查、记录或交换 commit，不设置跨机器认证状态；W3 完全不依赖本实验结果。

## 第一课时 · 看懂：“在我电脑上能跑”还缺什么

### 0-5 | 把绿色结果重新变成问题
> 程序能跑是一种现象；先弄清代码从哪里来、命令在哪里执行、运行条件由什么决定，现象才有意义。

#### 首问

> 同一段程序换一台电脑，为什么可能出现不同结果？

#### 不可遗漏

- 屏幕上的代码不是全部条件，解释器、依赖、当前目录和外部配置都会影响结果；
- 不同目录中的同名程序可能给出相似画面，不能只凭“看见绿色”判断自己做对了；
- 本周不要求学生编写程序，而是借一个很小的程序看清“取得、进入、恢复、运行、测试”之间的关系。

**转场：** 先把机器上到处可以调用的工具，与只属于某个项目的运行条件分开。

### 5-13 | 分开全局工具与项目局部环境
> 全局工具回答“这台机器能调用什么”，项目局部环境回答“这个项目按什么条件运行”。

#### 首问

> `git`、`uv`、Python 和某个项目需要的包，是不是都装在同一个地方？

#### 不可遗漏

- `git`、`uv` 通常可以为机器上的多个项目服务；
- `.python-version`、`pyproject.toml`、`uv.lock` 和 `.venv` 围绕当前项目组织；
- `.venv` 是根据项目声明在本机恢复出来的环境，不是从 GitHub 下载下来的文件；
- “全局／局部”描述作用范围和归属，不代表高级／低级或可靠／不可靠；
- 固定使用“项目局部环境”，避免与稍后的“本地仓库”混为一谈。

**转场：** 即使项目文件不变，程序还可以在启动时看到一项只属于当前命令的信息。

### 13-21 | 用 `COURSE_MODE` 看见运行时可见性
> 环境变量可以把运行时信息交给一个进程，而不必把它永久写进程序或项目文件。

本段只建立直觉，不要求记住命令，也不讲永久配置。

#### 完整演示

使用教师 Bash，让学生先预测每一步能否看见 `fixture`，再逐条执行：

```bash
unset COURSE_MODE
printenv COURSE_MODE
COURSE_MODE=fixture printenv COURSE_MODE
printenv COURSE_MODE
command -v uv
```

预期依次看到：空、`fixture`、再次为空，最后是本机 `uv` 的路径。只解释两点：

1. `COURSE_MODE=fixture` 只对紧随其后的进程可见；
2. shell 能找到 `uv`，是因为它会在已有搜索路径中寻找全局工具。

本周运行程序和测试时都会在命令前写 `COURSE_MODE=fixture`。它只是无敏感信息的课堂运行模式；不展示 token、Cookie、`.env` 或个人配置。

#### 固定退路

现场终端异常时直接展示以下预期记录，不排查个人 shell：

```text
（空）
fixture
（空）
/.../uv
```

**转场：** 现在把“全局工具、项目文件、局部环境”放进两种常见的 Python 环境管理方式。

### 21-31 | 用 uv 与 conda 比较环境怎样归属
> conda 常从“进入一个命名环境”出发，uv 常从“在这个项目中恢复并运行”出发；本课只实践 uv 路线。

不现场安装 conda，也不让学生同时维护两套路线。

#### 不可遗漏

- conda 的命名环境可以独立于某个项目目录存在；
- uv 更贴近以项目为中心的路线：项目用 `pyproject.toml` 声明需要什么，用 `uv.lock` 固定这次采用什么；
- conda 激活后改变当前终端看到的 Python，`uv run` 则明确在当前项目环境中执行命令；
- 两者都能用于隔离与复现，不能粗暴简化成“conda 是全局、uv 是局部”；
- 本课程统一使用 uv，只是为了让所有人沿一条较短、项目边界清楚的路线操作。

若有余时只补充一句：conda 还适合管理许多非 Python 依赖；不展开包格式和工具优劣争论。

**转场：** 环境回答“怎样运行”，接下来还要回答代码在本机还是远端、我们取得的是谁的修改。

### 31-43 | 从 local、remote 引出 Git
> local 是当前机器上的仓库，remote 是网络上共享的仓库；fork 与 clone 让一处远端修改来到另一台机器。

#### 用同一个场景介绍

1. 教师在 GitHub 上有课程仓库 `https://github.com/wxyinucas/ai-agents`；
2. 学生 fork 后拥有自己账号下的远端副本；
3. 学生在网页上把一处签名从 `teacher` 改成本人公开代号；
4. `git clone` 把这个远端副本完整取得到本机；
5. 同伴只要得到 fork URL，也能在另一台机器取得该副本。

#### 术语边界

- **项目局部环境／全局工具**：描述运行条件的归属；
- **本地仓库／远端仓库**：描述代码及其历史放在哪里；
- **fork**：在自己的 GitHub 账号下建立远端副本；
- **clone**：把某个远端仓库取得到本机新目录。

Git 会为网页修改留下版本记录，但本实验不查看编号，也不把 commit 当成判断条件。版本控制只科普到这里：它让变化有历史；以后真正需要精确指认版本时再使用 commit。

**转场：** 最后把这些概念压进一条马上能够亲手完成的路线。

### 43-50 | 看见本节实验的完整地图
> 本周只验证一件小事：同学在远端改掉的签名，能否在我的机器和项目环境中重新出现。

教师展示并逐项读完，不让学生此时开始操作：

```text
fork 课程仓库
→ 网页把 signature 从 teacher 改成本人代号
→ 只把 fork URL 交给同伴
→ 在自己的机器 clone 同伴 fork
→ 进入 warmups/week-02/course-check
→ uv 按锁文件恢复环境
→ 运行程序与测试并看见同伴签名
```

每一步的作用只说一句：fork 给自己一份远端副本；修改制造一个看得见的变化；clone 把变化带到本机；进入目录确定命令作用范围；同步恢复项目条件；程序展示事实；测试检查给定规则；同伴机器排除“只在我原来的目录里碰巧成功”。

明确任务名为“**不影响未来的本节课实验**”：它帮助理解本周概念，但不是 W3 的前置成果；本周未完成者也不会因此失去进入 W3 的资格。

## 第二课时 · 准备：让自己的签名进入 fork

### 0-9 | 先认识真实项目与输出
> `course-check` 是一个极小环境体检程序：它报告项目、版本、Python、局部环境、运行模式和签名，测试再检查这些字段是否符合本节规则。

#### 课前放行

只有下列条件已经在干净 WSL 中实测，才放行本课时：

- 唯一课程仓库可以公开访问和 fork：`https://github.com/wxyinucas/ai-agents`；
- 练习路径确定为 `warmups/week-02/course-check`；
- 每名学生已收到一个可以公开的课程代号，示例使用 `s07`；
- Git、uv 的唯一安装路线和教师备用环境已经准备；
- 教师已经实际走通“网页修改 → clone → sync → 程序 → pytest”；
- 错误目录、网络失败和仍显示 `teacher` 时的停止方式已经写入学生指南。

#### 项目只看六类文件

```text
warmups/week-02/course-check/
├── .python-version   希望使用哪一代 Python
├── pyproject.toml    项目名称、版本、Python 范围和依赖
├── uv.lock           本次采用的精确依赖版本
├── signature.toml    本节课唯一修改的签名
├── course_check.py   生成人能阅读的运行结果
└── tests/            从外部检查给定规则
```

TOML 只要求认出“分区、键和值”。学生稍后只改：

```toml
[student]
signature = "teacher"
```

`pyproject.toml` 与 `signature.toml` 使用同一种格式，但前者描述整个项目，后者只保存本节签名。

#### 版本号只分清两件事

- `python: 3.12.?` 是解释器版本；本课固定 3.12 系列，不要求补丁号完全相同；
- `version: 0.1.0` 是小项目版本，读作“主版本、次版本、修补版本”；这里只要求会辨认，不讲发布规则。

成功画面固定为 YAML-like 七行，其中 `s07` 换成本人代号：

```text
project: ai-agents-lab
version: 0.1.0
python: 3.12.?
project-env: PASS
course-mode: fixture
signature: s07
RUNTIME_CHECK=PASS
```

**转场：** 先由教师把完整路线跑一遍；学生知道终点画面以后，再去个人 fork 制造唯一变化。

### 9-20 | 教师完整示范一次，不让学生同步操作
> 教师示范负责给出全貌；学生只观察每一步在主流程中解决什么问题，下一段才开始网页操作。

教师使用一个签名已经改为 `s07` 的公开示例 fork，并从预先确认的空目录开始：

```bash
mkdir -p ~/course
cd ~/course
git clone "【教师示例 fork HTTPS URL】" ~/course/w02-demo
cd ~/course/w02-demo
git remote get-url origin
cd warmups/week-02/course-check
pwd
uv sync --locked
uv run --locked python -c 'import sys; print(sys.executable)'
COURSE_MODE=fixture uv run --locked python course_check.py
COURSE_MODE=fixture uv run --locked pytest -q
```

每到一步只停下来回答一句：

- clone：从哪个远端取得文件；
- `origin` 与 `pwd`：正在运行谁的仓库、哪一个练习目录；
- `uv sync --locked`：根据声明和锁文件恢复项目局部环境；
- `uv run`：从这个项目环境启动命令；
- 程序：把当前事实显示给人；
- pytest：检查教师预先写下的规则。

预期程序显示 YAML-like 七行，`signature: s07`，测试全部通过。教师故意不讲每条 Python 代码，也不让学生此时逐条跟输；示范失败时直接切换到课前保存的终端记录，不现场修演示机。

非常简短地连接实际工程：别人取得仓库、在新机器按项目文件恢复环境并跑测试，是“修改能否离开原电脑”的常见检查形状；本实验省略了正式工程中的精确版本和发布环节。

**转场：** 全貌已经看见；学生现在只负责准备一个带个人签名的 fork，不需要在本课时重复教师的终端路线。

### 20-32 | fork 并只改一处签名
> 网页修改的目的不是练习写代码，而是让自己的远端副本与教师原仓库出现一个肉眼可见的差别。

#### GitHub 网页固定动作

1. 打开 `https://github.com/wxyinucas/ai-agents`，确认仓库所有者是 `wxyinucas`；
2. 点击 **Fork**，在自己账号下建立公开 fork；已有个人 fork 时直接进入它，不再选择组织账号；
3. 在个人 fork 中依次进入 `warmups/week-02/course-check/signature.toml`；
4. 点击编辑按钮，只把 `teacher` 改为本人公开代号，例如：

   ```toml
   [student]
   signature = "s07"
   ```

5. 点击 **Commit changes...**，接受提交到个人 fork 的默认分支；按钮名称是网页操作的一部分，本实验不记录或交换 commit；
6. 返回文件页面，确认画面显示本人代号，并复制个人 fork 的 HTTPS URL。

不修改文件名、分区名或其他文件；不写姓名、学号、邮箱、密码或 token。网页顶部仍显示教师仓库、课程代号尚未确定，或文件内容不是上述两行时立即停止。

#### 到点退路

第 32 分钟停止 GitHub 账号与网页问题。没有完成者记录“个人网页步骤未完成”，随后保留同伴发来的 URL，第三课时仍可完成运行者角色；个人 fork 未完成不影响 W3。

**转场：** 网页修改已经完成；现在只检查这个远端副本是否能够通过一个 URL 被同伴找到。

### 32-39 | 确认并交换唯一 URL
> 同伴只接收个人 fork 的 HTTPS URL；签名答案应当由程序显示，而不是被提前告诉。

学生回到个人 fork 首页，依次确认：

1. 浏览器地址和页面所有者属于本人，而不是 `wxyinucas`；
2. `warmups/week-02/course-check/signature.toml` 中不再是 `teacher`；
3. **Code → HTTPS** 中复制的是个人 fork URL；
4. 把 URL 发给固定搭档，不附带 commit、公开代号、截图、压缩包或 `.venv`；
5. 收到搭档 URL 后只检查链接能否打开、页面是否为搭档 fork，不开始 clone。

三人组按照 A → B → C → A 环形交换，使每个人只收到一个 URL。链接打不开或指向教师仓库时，发送者在本段内重新复制一次；第 39 分钟仍不正确就保留真实结果，下一课时使用教师示例 URL 跟随。

**转场：** URL 已经交换；接下来只预检明天要用的 WSL、工具和空目录，不提前开始第三课时。

## 第三课时 · 看见：同学的签名来到我的机器

### 0-6 | 只交换一个 URL
> 实验问题已经足够简单：拿到同伴 fork URL，在自己的机器上重新建立环境，并亲眼看到同伴签名。

#### 课前放行

- 相邻两人固定成组；单数人数组成三人组并按 A → B → C → A 环形交换；
- 每人只发送个人 fork 的 HTTPS URL，不发送 commit、公开代号或运行截图；
- 每台机器确认 `~/course/w2-peer` 不存在；存在时只使用固定备用目录 `~/course/w2-peer-2`，两者都存在则停止 clone；
- 教师准备一个签名已经不是 `teacher` 的公开示例 fork，以及已经恢复好的示例环境；
- 明确核验同学的 fork 不要求登录同学账号，也不接触任何密码或 token。

教师给出唯一判断：程序和测试能运行，且 `signature:` 后面出现同伴公开代号而不是 `teacher`。签名只是本节可见标记，不是身份、作者或能力证明。

**转场：** 第一轮由 A 发送 URL，B 在 B 自己的机器上从空目录开始。

### 6-20 | B 在自己的机器上运行 A 的 fork
> B 看到的签名必须来自刚刚 clone 的 A 的 fork，而不是 A 的电脑、截图或口头说明。

B 把 A 的 URL 填进唯一占位并执行；A 只观察，不碰 B 的键盘：

```bash
mkdir -p ~/course
cd ~/course
git clone "【A 的 fork HTTPS URL】" ~/course/w2-peer
cd ~/course/w2-peer
git remote get-url origin
cd warmups/week-02/course-check
uv sync --locked
COURSE_MODE=fixture uv run --locked python course_check.py
COURSE_MODE=fixture uv run --locked pytest -q
```

B 依次确认：`origin` 是 A 的 URL；当前目录是本周练习；程序输出中的签名不是 `teacher`；程序出现 `project-env: PASS`、`course-mode: fixture` 与 `RUNTIME_CHECK=PASS`；pytest 全部通过。运行前不打开 `signature.toml` 提前寻找答案。

若使用固定备用目录 `w2-peer-2`，只替换 clone 目标和随后进入的目录名，其他命令不变。

#### 到点退路

任何一步失败都停在真实画面：目录占用不删除，网络失败不换下载方式，同步失败不重建环境，签名仍为 `teacher` 时不在 B 的本地副本修改。B 只告诉 A“我在哪一步看到了什么”；本节不把排障升级成结对改项目。

第 20 分钟停止第一轮。

**转场：** 保留 B 的观察，交换方向；第一轮的故障不占用第二轮时间继续抢救。

### 20-34 | A 在自己的机器上运行 B 的 fork
> 交换角色以后仍然只用 URL 和同一组命令；判断标准不随人改变。

B 把个人 fork URL 发给 A。A 在自己的机器上执行上一段完全相同的路线：

```text
确认 w2-peer 目标目录为空
→ clone B 的 fork
→ 核对 origin
→ 进入 warmups/week-02/course-check
→ uv sync --locked
→ COURSE_MODE=fixture 运行程序并观察 signature
→ COURSE_MODE=fixture 运行 pytest
```

A 亲自操作，B 只观察；成功标准与停止条件和第一轮相同。三人组不做三轮串行演示，而是在 6–34 分钟内同时完成环形交换，使每个人恰好运行一位同学的 fork，也恰好有一位同学运行自己的 fork。

第 34 分钟无条件停止第二轮。没有完成不需要补出一个绿色结果，直接保留“未通过”。

**转场：** 两轮结束后不再继续跑命令；最后只讨论我们真正观察到了什么。

### 34-40 | 区分程序、测试与人的观察
> 程序显示当前事实，测试检查预先写好的规则，人负责说明这两份结果究竟支持什么结论。

教师使用预先准备的画面，不等待自愿展示，比较三种情况：

1. 输出仍是 `signature: teacher`：取得了教师原版或尚未修改的 fork，本节目标没有出现；
2. 输出是同伴代号但 pytest 失败：签名变化已经来到本机，但其他项目条件没有通过；
3. 输出是同伴代号且 pytest 通过：本节小实验完成。

只形成两句共同结论：

- 能说明：同伴 fork 中的一处变化，可以随仓库来到我的机器，并在重新恢复的项目环境中被程序和测试看见；
- 不能说明：这是谁亲自写的、整个项目都正确、所有机器都会成功，或以后课程必须依赖这次结果。

非常简短地连接实际工程：新机器重新取得仓库、恢复环境并跑测试，是团队检查“修改能否离开原作者电脑”的常见缩影；本实验只体验形状，不承担正式发布职责。

第 40 分钟停止展示、讨论与排障。

**转场：** 最后十分钟不再制造新证据，只留下三行真实观察。

### 40-50 | 三行收口，然后与 W3 解耦
> 记录只回答本节实验发生了什么；无论通过与否，W3 都从自己的新任务独立开始。

每人只填写：

```text
我的机器：通过 / 未通过
看到的同学代号：
一项观察：
```

“通过”表示：从同伴 fork URL 新 clone；进入 `warmups/week-02/course-check`；按锁文件完成环境同步；程序显示同伴签名而不是 `teacher`；程序与 pytest 均通过。任一环节没有实际发生就写“未通过”；没有看到代号时写“未看到”，不猜测、不补填。

“一项观察”只写一句自己真正看见的现象，例如“换了一台机器，`.venv` 路径不同，但程序仍显示同学的签名”。不要求解释全部代码，不保存长篇报告，也不设置额外状态。

最后两分钟教师明确：W3 不读取本实验的 fork、目录、记录或结果；这些本地目录只属于本节课堂练习。未通过者若想课后重试可继续使用本周指南，但不以补做换取进入后续课程的资格。

## 临场取舍

- 慢了 · 删什么：第一课时删 conda 的扩展用途，只保留环境归属差异；第二课时严格守住 20、32、39、46 分钟的分段边界，未完成部分切到教师示例；第三课时保住双方各运行一个 URL 和最后十分钟三行收口，删案例扩展。
- 快了 · 做什么：让学生用一句话分别解释程序输出与 pytest 各自做了什么，或从新终端重新进入练习目录运行一次；不增加 commit、分支、push 或 W3 内容。
- 坏了 · 怎么退：使用教师示例 fork 和已恢复环境演示同一条路线；学生仍按真实情况写“未通过”，同时完成“看到的同学代号／一项观察”中确实能够填写的部分。

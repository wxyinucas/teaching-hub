# W3｜Agent 改完以后，凭什么保留？

> AI Agents · W3 · 3 × 50 min · 约 25 名零编程基础学生 · 无助教

## 本次课

- 根问题：Agent 修改了项目，我们凭什么决定保留这次修改？
- 最低出口：完成一次“受控修改 → 检查 diff → 运行测试 → commit/push”的责任闭环，解释一个测试，并产生明确标注 fixture 的观察摘要。
- 硬收口：第二课时第 35 分钟停止新增修改；第三课时第 40 分钟停止展示，末 10 分钟只保存决定、证据、卡点和下一步。

## 第一课时 · 看懂：建立起点，看见一次受控修改

### 0-18 | 从教师项目走到个人版本
> 修改之前，先建立一个来源清楚、能够由本人保存的工作起点。

用 W2 的可复现项目辨认三个位置，再按教师任务卡在课堂内建立并核验个人 fork 与远端关系：

- `upstream`：教师维护的课程来源；
- local：Agent 实际读取与修改的本地项目；
- `origin`：学生个人 fork，接收本人检查后的 push。

本段不是课前通关条件。W2 尚未通关或 fork 配置失败者保留真实 `BLOCKED-*`，使用教师副本继续理解后面的责任链。

**收口：** 回答了版本从哪里来、将去哪里；留下 `origin/upstream/local` 的核验结果；下一段建立 Agent 入口。

### 18-32 | 让本地 Agent 达到可用起点
> 本周先证明 Agent 能在正确项目中响应，不在安装细节里无限停留。

全班只走课程冻结的一条安装、登录与健康检查路线。检查 Agent 当前工作目录，让它只读取项目并复述任务入口，尚不允许修改。

第 32 分钟统一停止配置。失败者保留 `BLOCKED-AGENT`，改用教师预制 diff 参与审查；fallback 不算完成 Agent 实作。

**收口：** 回答了 Agent 能否进入正确项目；留下可用或受阻状态；下一段观察人怎样接管 Agent 的结果。

### 32-50 | 教师演示“要求到决定”的责任链
> Agent 可以执行修改，人负责限定范围、判断证据并决定是否保留。

使用一个只有单一行为变化的预制任务，依次停在：

```text
任务与范围 → Agent 计划 → 实际 diff → 给定测试 → ACCEPT / HOLD
```

先展示正常版本，再展示一个“测试通过，但顺手改了锁文件或任务范围外文件”的版本。只追问：改了什么、测试证明什么、为什么仍可能拒绝。随后学生写下：

```text
本次唯一目标：
允许 Agent 修改：
我会运行的测试：
我只有在什么条件下才接受：
```

**收口：** 回答了为什么绿色测试不是唯一条件；留下本次任务的接受条件；下一课时只执行这一项修改。

## 第二课时 · 做成：完成一次责任闭环

### 0-10 | 核对起点并发出任务
> 工作区、远端和任务边界清楚以后，Agent 才开始修改。

学生确认当前目录、工作区状态、`origin/upstream` 和 W2 测试，再使用 `guide.md` 的简短 Prompt。无法解释的旧修改必须先停止。

**收口：** 回答了 Agent 是否可以开始；留下任务边界与干净起点；下一段观察实际修改。

### 10-35 | Agent 修改，人检查 diff 与测试
> 第 35 分钟以后不再增加功能，只判断已经发生的修改。

学生检查所有变动文件、关键 diff 和给定测试，并解释其中一个测试的输入、预期与实际结果。测试通过但范围越界或改动无法解释时选择 `HOLD`。

教师只观察：Agent 是否在正确目录、计划是否越界、学生是否在越界前叫停。Agent 故障者使用预制 diff 完成审查。

**收口：** 回答了改动是否符合规格与范围；留下 diff、测试和一项解释；下一段作出提交决定。

### 35-50 | 决定、commit 并 push
> 提交的是学生已经检查并愿意负责的版本，而不是 Agent 的“完成”。

只有 `ACCEPT` 才进入暂存、再次检查 staged diff、commit 和 push。`HOLD` 保留未接受的证据；push 失败者保留本地 commit 与完整错误。

不使用 `git add .`，不提交密码、token、`.env`、账户信息、原始平台响应或任务范围外文件。

**收口：** 回答了哪个版本值得保存；留下 commit/push 或明确的 `HOLD/BLOCKED`；下一课时用 fixture 观察并展示责任链。

## 第三课时 · 说清：展示一次接受决定

### 0-10 | 运行平台形状 fixture 并冻结证据
> 本周观察程序怎样接触平台形状，不把模拟数据冒充真实平台。

学生运行任务卡中的唯一 `observe` 命令，输出必须显式标注 `execution_mode=fixture`。真实 Longbridge 连接不是 W3 通关条件。

fixture 支持格式与处理链检查；它不证明数据来自真实市场、已连接券商或策略会盈利。

**收口：** 回答了本次观察使用什么数据；留下带运行模式的摘要；下一段让同伴核对完整链路。

### 10-35 | 同伴核验五项证据
> 展示目标是让另一人复核决定，不是复述完整开发过程。

两人一组，各自说明任务、实际 diff、接受或拒绝、测试与版本证据、fixture 的证据边界。核验者只追问一处关键 diff、一个测试和一项仍未知内容。

**收口：** 回答了自己的接受决定能否被他人复核；留下一条同伴追问；下一段比较有差异的决定。

### 35-50 | 抽样讨论并完成门槛 0 收口
> 比较 `ACCEPT/HOLD/BLOCKED` 的理由，不现场修复个人项目。

教师优先抽取一份范围清楚的 `ACCEPT`、一份测试通过但选择 `HOLD` 的案例和一份可接续的 `BLOCKED-*`。第 40 分钟停止展示，学生保存：

```text
完成程度：complete / partial / blocked
发布决定：ACCEPT / HOLD / BLOCKED
当前 commit：
观察模式：fixture
本周证据支持：
本周证据不能支持：
下一步：
```

**收口：** 回答了为什么保留这个版本；留下可复核的责任链；W4 从明确标注来源的观察摘要进入真实数据。

## 临场取舍

- 慢了 · 删什么：删第二个演示、GitHub 页面操作和自由讨论；保住任务边界、diff、测试、提交状态与 fixture 摘要。
- 快了 · 做什么：处理一个预制故障，例如改错目录、修改锁文件、删除失败测试或测试绿但规格错误。
- 坏了 · 怎么退：Agent 故障用预制 diff，GitHub 故障保留本地 commit，fixture 故障用预存摘要；相应状态保持 `BLOCKED-*`。

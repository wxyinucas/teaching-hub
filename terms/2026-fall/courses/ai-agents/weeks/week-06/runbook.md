# W6｜函数、调用与可见性

> 3 × 50 min · 六个场景依次预测、运行、修复；题目、错误代码、检查与折叠参考均在 Notebook 中。

## 知识地图

- **Road map：找到名字 → 跟踪调用 → 判断共享 → 修复并核验**
  - 名字：函数参数与函数外变量；定义环境与调用位置。
  - 调用：返回函数、闭包与 nonlocal；递归每层的参数和返回值。
  - 共享：默认列表、显式传入的容器、导入的名字与对象。
  - 综合：同一实例共享状态；不同计数器、快照与分支保持独立。

## 本次课 · 读懂错误代码，预测流程，再修复

#### 场景一｜函数外的变量与同名参数，读到的会是谁？

- 对齐三份值：公共 `threshold = 10`、公共 `offset = 2`、传给 `caller` 的参数 `4`。需求是 `4 + 2 = 6`，公共基准仍为 `10`。
- 先看错误输出：`caller_trial` 内的参数是 `4`，`read_threshold_trial()` 却返回 `10`，最后算出 `12`。
- 保留 `read_threshold()` 读取公共基准；把 `caller(threshold)` 的计算修为 `threshold + offset`。读取函数按自己的定义环境找名字，不会取得调用者的同名参数。
- 核验：只把公共 `threshold` 改成 `20`，`caller(4)` 仍为 `6`，读取函数返回 `20`；再把 `offset` 改成 `3`，计算才变成 `7`。调用不改公共变量。

#### 场景二｜同时维护两组累计值，为什么会串到一起？

- 先用补充例子确认：`return double` 返回函数，`f(3)` 才调用它。返回函数继续引用外层变量形成闭包；`nonlocal current` 指定内层赋值更新外层已有的变量。
- `make_counters([10, 100])` 返回两个更新函数。交替调用 `a()`、`b(2)`、`a(3)`、`b(0)`，需求是 `[11, 102, 14, 102]`；错误版得到 `[101, 103, 106, 106]`。
- 指认错误版只有一份 `current`：`for` 不为每轮创建函数作用域，两个 `advance` 都从循环结束后的 `100` 继续改它。
- 修复抓手：`make_one(start)` 内建立 `current` 并返回 `advance`；外层用显式 `for` 循环，每轮调用一次 `make_one(start)`，再加入列表。`nonlocal` 的含义不变，独立状态来自不同的函数调用。
- 核验交替调用、重复起点、零与负增量、空输入；另一轮创建不接续旧状态，修改原起点列表也不影响已有计数器。

### 50-100 | 调用结束之后，哪些数据还会留下？

> 用调用轨迹区分每层局部变量，用连续调用检验容器是否共享。

#### 场景三｜函数调用自己以后，每一层还记得原来的参数吗？

- `sum_trace(2)`：先进入 `2 → 1 → 0`，再返回 `0 → 1 → 2`，各层累计和为 `0 → 1 → 3`。对照完整 `events`，不只看 `total`。
- 错误版先做 `x -= 1`，改掉本层的加数和返回日志；这是本层重新赋值造成的，不是子调用改了上层变量。
- 修为 `subtotal = x + visit(x - 1)`：保留本层 `x`，只将减一后的值传给下一层。日志记录真实递归过程，不用公式另造轨迹。
- 核验 `x = 0` 仍有进入和返回记录；同次求和共用一份日志，不同 `sum_trace` 调用新建日志，后一次不改前一次结果。

#### 场景四｜第二轮结果，为什么多了第一轮的数据？

- 先用 `scale(value, factor=2)` 对照省略参数、按位置传入与按名称传入；再看 `collect_batches(batches, target=None)` 的两个参数。
- 错误版的 `target=[]` 在定义函数时创建。两次默认调用共用列表，第二轮追加 `9` 后，第一轮结果也成了 `[1, 2, 3, 9]`。
- 默认值改为 `None`，仅在 `target is None` 时新建列表；显式传入列表则向原对象末尾追加并返回它。传入 `[]` 也属于显式共享，不能用真假判断替代 `is None`。
- 核验默认两轮分别得到 `[1, 2, 3]`、`[9]`；给定 `[100]` 后得到 `[100, 4, 5, 6]`，且 `result is target`。再看空批次、显式 `None` 与原始输入保持。

### 100-150 | 哪些状态共享，哪些数据必须独立？

> 从模块配置到状态分叉，明确共享范围，用交错操作核验隔离。

#### 场景五｜为新实验生成一份可独立修改的配置

- 运行前预测三处：`from defaults import *` 把本程序的 `seed = 7` 覆盖成 `42`；返回的标签共用公共列表；修改 `defaults.limit` 后，导入的 `limit` 仍为旧值 `3`。
- `make_run_config(requested_seed)` 用传入的种子、当前 `defaults.limit` 和 `defaults.labels.copy()` 生成新字典；保留本程序已有的 `seed`。
- 对照参考的两种位置：函数外或函数内均可 `import defaults`。函数内导入只让模块名成为局部名字，不会自动隔离模块数据，标签仍需复制；函数内不能写 `from defaults import *`。
- 修复后先重跑输入格，再运行修复后的导入、函数与检查。删掉星号导入的源代码，不会撤销已经发生的名字覆盖和列表修改；不在修复函数中重设 `seed` 掩盖问题。
- 核验：改第一份标签不影响公共标签和第二份配置；公共上限改成 `5` 后，新配置读取 `5`，旧配置仍保留 `3`。

#### 场景六｜从同一个累加进度，分别继续计算

- `make_accumulator(start=0)` 返回 `add`、`snapshot`、`fork`。同一实例的三个函数应共享当前值与历史；不同实例、分支和快照需要独立。
- 沿一次操作预测：从 `10` 加 `2`，保存快照并分叉；原路线加 `3` 得 `15`，新路线加 `-5` 得 `7`；旧快照仍为 `12`，只有第一条历史。
- 错误版的数值分别更新，历史却共用列表；旧快照继续增长，修改其中一条字典也会波及其他结果。值正确不代表隔离正确。
- 修复抓手：保留同次 `build` 内的共享，在 `snapshot()` 导出和 `fork()` 建立分支时分别使用 `deepcopy(history)`；只复制外层列表仍会共用记录字典。
- 核验完整历史、修改旧快照的嵌套记录、再次分叉、零增量也留记录，以及重新创建实例。可与 Agent 合作补一组不同输入，再亲自运行检查；使用函数与闭包，不引入 `class` 或模块全局累加器。
- 收束时回到三问：名字从哪里找到？哪次调用持有这份状态？改的是名字绑定还是对象内容？用另一份输入、连续或交替调用核验修复，保留公开检查的预期。
